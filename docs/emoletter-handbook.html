개요

무엇을 만드는 서비스이고, 저장소가 어떻게 나뉘어 있는가

EmoLetter는 두 가지 기록을 다룬다. 하나는 감정 일기로, 날짜마다 감정 하나와 글을 남기면 달력 칸에 해당 이모지가 표시된다. 다른 하나는 타임캡슐 편지로, 받을 날짜를 지정해 글을 써두면 그 날짜가 지나야 열어볼 수 있다.

저장소는 프론트엔드와 백엔드가 한 리포지터리에 나란히 들어있는 모노리포 구조다.

디렉터리내용기술
EmoLetter_FE/ 웹 프론트엔드. 달력·일기·편지함 UI 전체 React 19, Vite 6, Tailwind CSS 3
EmoLetter_BE/ REST API 서버. 인증·일기·편지 도메인 Spring Boot 3.2, JPA, Spring Security, JWT
.github/workflows/ EC2 배포 파이프라인 현재 중단 GitHub Actions, DockerHub

도메인 모델

백엔드 엔티티는 세 개다. User가 Diary와 Letter를 각각 1:N으로 소유한다.

엔티티주요 필드비고
User userId(PK, String), email, nickname, password, role, createAt PK가 숫자가 아니라 사용자가 정한 아이디 문자열이다. 비밀번호는 BCrypt로 저장
Diary diaryId, content, emojiCode, createAt, user emojiCode는 자유 문자열 컬럼이라 감정 종류를 프론트에서 늘려도 스키마 변경이 없다
Letter letterId, title, content, noteCode, deliverDate, isDelivered, isOpened, createAt, user title은 2026.08.27 추가. 그 전 편지를 위해 nullable이다
RefreshToken userId(key), refreshToken MySQL이 아니라 Redis에 저장된다. TTL 24시간
편지의 두 가지 상태 플래그

isDelivered는 “받을 날짜가 지나 열람 가능해졌는가”, isOpened는 “사용자가 실제로 열어봤는가”를 뜻한다. 서로 다른 개념이라 둘 다 필요하다. isDelivered는 백엔드 스케줄러가 매분 갱신하고, isOpened는 상세 조회 API가 호출될 때 켜진다.

시스템 구성

로컬에서 요청이 흐르는 경로와 각 포트의 역할

왜 Vite 프록시를 쓰는가

브라우저가 5173에서 8080을 직접 부르면 다른 오리진이므로 CORS 예비 요청이 필요하고, 로그인 시 백엔드가 내려주는 refreshToken 쿠키가 httpOnly + 크로스 오리진이라 전송 조건이 까다로워진다. 프록시를 두면 브라우저 입장에서는 전부 같은 오리진이라 이 두 문제가 동시에 사라진다.

프록시를 쓰지 않고 배포 환경처럼 직접 호출하는 경우를 대비해 백엔드에도 CORS 설정을 넣어두었다. refreshToken 쿠키를 주고받아야 하므로 allowCredentials=true이고, 그 경우 와일드카드 오리진을 쓸 수 없어 주소를 명시했다.

기능 상세

인증, 일기, 편지 세 흐름이 실제로 어떻게 동작하는가

인증과 세션

로그인에 성공하면 백엔드는 두 개의 토큰을 만든다. accessToken은 응답 본문에 담겨 오고, refreshToken은 httpOnly 쿠키로 내려온다. 프론트는 accessToken만 localStorage에 보관하고 모든 요청에 Authorization: Bearer로 붙인다.

  • 세션 복구 — 새로고침하면 AuthContext가 저장된 토큰으로 GET /api/user를 호출해 사용자 정보를 되살린다. 실패하면 토큰을 버린다.
  • 복구 중 깜빡임 방지 — initializing 상태 동안 헤더는 빈 자리만 잡아두어 로그인 버튼이 잠깐 나타났다 사라지지 않는다.
  • 401 처리 — http.js가 401을 받으면 등록된 콜백으로 세션을 정리한다.
  • 로그아웃 — DELETE /api/user/logout으로 서버의 refreshToken을 지우고 쿠키를 만료시킨다. 서버가 실패해도 클라이언트 세션은 반드시 정리한다.
토큰 자동 재발급 (2026.08.27 해결)

POST /api/token이 쿠키에서 refreshToken을 읽도록 바뀌면서 프런트에서도 재발급을 호출할 수 있게 됐다. 이제 401을 받으면 재발급을 한 번 시도하고 원래 요청을 재시도한다. 재발급까지 실패했을 때만 세션을 정리한다. 자세한 내용은 변경 이력 참고.

타임캡슐 편지

편지 목록 API는 isOpened 파라미터가 필수라 “전체”를 한 번에 받을 수 없다. 그래서 true와 false로 두 번 호출한 뒤 합쳐서 보낸 날짜 최신순으로 정렬한다.

받은 편지함은 별도 엔드포인트가 아니라 이 목록에서 도착한 것만 거른 결과다. 도착 판정은 백엔드 스케줄러의 isDelivered를 우선 보되, 아직 반영되지 않았어도 받을 날짜가 지났으면 도착한 것으로 취급한다. 스케줄러가 1분에 한 번 도니 그 사이 공백을 메우기 위한 것이다.

편지를 누르면 useLetterReader가 도착 여부를 먼저 확인한다. 아직이면 열지 않고 “아직 받을 날짜가 되지 않은 편지예요”를 띄우고, 도착했으면 상세 조회를 호출한다. 이 호출 자체가 백엔드에서 읽음 처리를 겸한다.

핵심 코드 해설

읽을 때 헷갈리기 쉬운 네 곳

http.js — 모든 요청이 지나는 길목

토큰 부착, 쿠키 동봉, 에러 메시지 변환, 401 감지를 한곳에서 처리한다. 각 API 모듈은 경로와 본문만 신경 쓰면 된다.

  • 토큰 보관 — 메모리 캐시 + localStorage 이중. 매 요청마다 스토리지를 읽지 않는다.
  • credentials: 'include' — refreshToken 쿠키가 함께 전송되도록 모든 요청에 붙인다.
  • 에러 변환 — 상태 코드별 한국어 기본 문구를 두고, 서버가 message나 errors를 주면 그쪽을 우선한다. 네트워크 자체가 실패하면 status 0으로 “서버에 연결할 수 없습니다”를 낸다.
  • 401 콜백 — AuthContext가 등록한 핸들러를 호출해 세션을 정리한다. 순환 참조를 피하려고 컨텍스트를 직접 import하지 않고 콜백을 주입받는 구조다.

date.js — toISOString을 쓰면 안 되는 이유

백엔드는 LocalDateTime을 쓴다. 타임존이 없는 “벽시계 시각”이다. 그런데 toISOString()은 값을 UTC로 바꿔버린다. 한국 시간 기준으로 8월 22일 새벽 2시는 UTC로 8월 21일 17시가 되어, 저장된 일기의 날짜가 하루 밀린다. 그래서 문자열을 직접 조립한다.

useAppNavigation — writeMode가 필요한 이유

달력에서 날짜를 누르면 보통 일기 작성으로 간다. 그런데 사용자가 메뉴에서 “편지 보내기”를 고른 뒤에는 같은 클릭이 편지 작성으로 가야 한다. 이 “지금 어느 모드인가”를 writeMode가 기억한다.

ViewRouter — 화면 보호

일기 작성, 편지 작성, 두 편지함은 로그인이 필요하다. 각 컴포넌트마다 검사하지 않고 라우터 한곳에서 목록으로 관리한다.

응답 정규화

백엔드 DTO를 그대로 쓰지 않고 toDiary, toLetter, toUser로 한 번 변환한다. nickName처럼 대소문자가 다른 필드, 날짜 문자열을 Date로 바꾸는 작업, 그리고 Lombok 게터 때문에 isOpened가 opened로 직렬화될 수 있는 상황을 이 지점에서 흡수한다. 덕분에 컴포넌트는 항상 같은 모양의 객체만 본다.

토큰 자동 재발급이 동작하도록 수정

기능

controller/TokenApiController.java · src/api/http.js

왜

POST /api/token이 refreshToken을 요청 본문으로만 받았다. 그런데 그 토큰은 로그인 시 httpOnly 쿠키로 내려가기 때문에 브라우저의 자바스크립트가 값을 읽을 수 없다. 즉 프런트에서는 재발급 요청 자체를 만들 수 없었다.

결과적으로 accessToken 유효기간 1시간이 지나면 사용자가 아무 잘못 없이 로그아웃됐다.

어떻게

백엔드는 쿠키를 먼저 읽고, 없을 때만 본문 값을 쓰도록 바꿨다. 쿠키를 쓰지 않는 모바일 클라이언트를 위해 기존 방식도 남겨두었다. 둘 다 없으면 401을 반환한다.

프런트는 http.js에서 401을 받으면 재발급을 한 번 시도하고 원래 요청을 재시도한다. 재발급까지 실패했을 때만 세션을 정리한다.

결과

토큰이 만료돼도 사용자는 눈치채지 못하고 하던 작업을 이어간다.

프런트에서 신경 쓴 것은 동시 요청과 무한 재시도 두 가지다. 달력 화면은 일기와 편지를 동시에 부르기 때문에 401이 한꺼번에 여러 개 올 수 있다. 그때마다 재발급을 호출하면 토큰이 여러 번 갈린다. 그래서 진행 중인 Promise를 공유해 재발급은 한 번만 일어나게 했다.

재시도는 retry 플래그로 딱 한 번만 허용한다. 재발급 요청 자체에는 retry: false가 붙어 있어 그 요청이 401을 받아도 다시 재발급을 시도하지 않는다. 또 애초에 토큰이 없던 요청은 재발급해도 소용없으므로 건너뛴다.

인증 실패 시 403 대신 401 반환

보안

config/WebSecurityConfig.java

왜

Redis 기본 호스트를 127.0.0.1로

설정

resources/application.yml

왜

결과

왜

검증하는 동안 Redis가 반복해서 죽었다. 원인은 Redis가 아니라 WSL이었다. WSL2는 아무도 쓰지 않으면 가상머신을 내리는데, 그때 수동으로 띄운 데몬도 함께 사라진다.

어떻게

이 배포판은 systemd가 켜져 있어서 서비스로 등록할 수 있었다. wsl -u root는 비밀번호 없이 들어가지므로 sudo 비밀번호도 필요 없었다.

기본 redis.conf는 127.0.0.1에만 바인딩해 윈도우에서 닿지 않으므로 bind 0.0.0.0으로 바꿨다. (원본은 redis.conf.bak으로 백업)

결과

WSL이 뜰 때마다 Redis가 자동으로 시작된다. 수동 실행 명령을 외울 필요가 없다.

남은 제약

WSL 자체가 유휴 상태로 내려가면 Redis도 함께 멈춘다. wsl 명령을 한 번 실행하면 다시 부팅되면서 서비스가 자동으로 살아난다. 완전히 막으려면 %UserProfile%\\.wslconfig의 [wsl2]에 vmIdleTimeout=-1을 넣으면 된다. 전역 설정이라 적용하지 않았다.

오류 응답 분리 — 사용자에겐 안내, 개발자에겐 원인

기능

config/GlobalExceptionHandler.java (신규) · dto/error/ErrorResponse.java (신규) · run-local.ps1

왜

Redis가 죽었을 때 로그인이 실패하는데, 사용자 화면에는 “권한이 없습니다”나 “서버에 문제가 발생했습니다”만 떴다. 사용자는 뭘 해야 할지 모르고, 개발자는 원인을 찾으려면 스택트레이스를 뒤져야 했다.

반대 방향의 문제도 있었다. 비밀번호가 틀리면 서비스가 IllegalArgumentException("Invalid Password Your Id : testuser1")을 던지는데, 이런 메시지가 그대로 클라이언트에 나가면 아이디 존재 여부가 노출된다.

어떻게

@RestControllerAdvice로 예외를 한곳에서 받아 두 갈래로 나눴다. 응답에는 사용자가 읽을 문장만 담고, 콘솔에는 원인과 조치 방법을 남긴다.

콘솔 메시지는 스택을 끝까지 타고 내려가 근본 원인을 뽑아내고, “무엇을 실행하면 되는지”까지 함께 찍는다. 로그만 봐도 조치가 가능하도록 했다.

결과

실제 콘솔 출력

로그 레벨을 구분했다

서버 장애(Redis·DB·예상 못한 예외)는 log.error로 스택트레이스까지 남기고, 토큰 만료나 비밀번호 오류처럼 정상적인 흐름은 log.warn으로 한 줄만 남긴다. 사용자가 비밀번호를 틀릴 때마다 스택트레이스가 쌓이면 진짜 장애가 묻히기 때문이다.

로그인 실패는 전용 예외로 분리했다

처음에는 로그인 실패도 IllegalArgumentException에 묶여 “요청을 처리할 수 없습니다”라는 막연한 문구가 나갔다. 로그인 폼에서는 도움이 되지 않는다. 그래서 사용자용 문구와 로그용 상세를 따로 들고 다니는 예외를 만들었다.

핵심은 아이디가 없을 때와 비밀번호가 틀릴 때 같은 문구를 내보내는 것이다. 다르게 응답하면 아이디가 존재하는지 여부를 외부에서 알아낼 수 있다.

WSL Redis가 끊기는 문제를 스크립트에서 처리

운영

EmoLetter_BE/run-local.ps1

왜

로컬 개발 내내 Redis가 반복해서 끊겼다. 원인은 Redis가 아니라 WSL2였다. WSL2는 vmIdleTimeout 기본값에 따라 약 1분간 아무도 쓰지 않으면 가상머신을 통째로 내린다. 그 안에서 돌던 Redis도 함께 사라진다.

증상이 헷갈렸던 이유는 일부 요청만 실패했기 때문이다. 비밀번호가 틀린 로그인은 Redis에 닿기 전에 끝나서 401이 정상적으로 나오는데, 성공하는 로그인만 refreshToken 저장 단계에서 503이 났다.

어떻게

전역 설정(%UserProfile%\\.wslconfig의 vmIdleTimeout)을 바꾸면 해결되지만, 그러면 모든 WSL 배포판이 항상 메모리를 붙잡고 있게 된다. 이 프로젝트 하나 때문에 시스템 전체 동작을 바꾸는 건 과했다.

대신 run-local.ps1이 두 단계로 처리하게 했다.

  • 기동 전 — 6379가 죽어 있으면 WSL에 명령을 하나 보내 깨운다. redis-server가 systemd 서비스로 등록돼 있으므로 부팅과 함께 따라 올라온다.
  • 기동 중 — WSL 안에 sleep 프로세스를 하나 띄워 서버가 도는 동안만 VM을 붙잡아 둔다. 스크립트가 끝나면 정리한다.
결과

개발 세션 동안 Redis가 끊기지 않고, 스크립트를 끄면 WSL도 평소대로 잠든다.

한 번만 해두면 되는 사전 작업

위 방식은 redis-server가 WSL의 systemd 서비스로 등록돼 있다는 전제 위에 있다. 등록은 한 번만 하면 되고, wsl -u root는 비밀번호 없이 들어가므로 sudo 암호도 필요 없다.

IntelliJ로 띄울 때는 적용되지 않는다

이 처리는 run-local.ps1을 거칠 때만 동작한다. IntelliJ 실행 구성으로 띄우면 WSL이 여전히 잠들 수 있다. 그때는 wsl -u root -- systemctl start redis-server를 한 번 실행하거나, 전역 설정을 쓰는 편이 낫다.

MySQL 호스트 환경변수화 — 시도했다가 되돌림

되돌림

resources/application.yml (원상복구)

왜

Redis와 같은 이유로 JDBC URL의 localhost도 ${DATABASE_HOST:localhost}로 바꾸려 했다. .env에 DATABASE_HOST가 이미 있는데 아무 데서도 쓰이지 않고 있었기 때문이다.

문제

바꾸고 기동해 보니 백엔드가 DB에 붙지 못했다. 로컬 .env의 값이 DATABASE_HOST=mysql, 즉 Docker 서비스 이름이었다. 로컬에는 존재하지 않는 호스트다. 그동안 이 변수가 무시되고 있었기에 아무 문제가 없었던 것이고, 갑자기 읽기 시작하자 로컬 실행이 깨졌다.

조치

JDBC URL을 원래대로 localhost로 되돌렸다. Redis 쪽은 REDIS_HOST가 .env에 없어 기본값이 그대로 쓰이므로 안전하게 유지했다.

제대로 고치려면 로컬 .env의 DATABASE_HOST를 localhost로 바꾸거나 (이 값은 배포용 SPRING_ENV_FILE 시크릿과 별개다), .env에 없는 새 변수명을 쓰면 된다. 지금은 로컬 실행 안정성을 택했다.

MySQL 호스트를 환경변수로 (되돌렸던 작업의 재시도)

설정

application.yml · docker-compose.yml

왜

바로 위 항목에서 DATABASE_HOST 환경변수화를 시도했다가 되돌렸다. 로컬 .env에 DATABASE_HOST=mysql(도커 서비스 이름)이 들어 있어 로컬 실행이 깨졌기 때문이다. 그래서 JDBC URL은 localhost 고정으로 남아 도커로 배포하면 DB에 닿지 못하는 상태였다.

어떻게

문제의 원인은 "환경변수를 쓰는 것"이 아니라 하필 이미 다른 값이 들어 있는 이름을 골랐다는 데 있었다. 그래서 .env에 존재하지 않는 새 이름 MYSQL_HOST를 쓰기로 했다. Redis가 REDIS_HOST로 이미 잘 동작하고 있던 방식과 똑같다.

  • 로컬 — .env에 MYSQL_HOST가 없으니 기본값 localhost가 쓰인다
  • 도커 — compose가 MYSQL_HOST: mysql을 넘겨 컨테이너 이름으로 찾아간다

.env를 고치지 않아도 되므로 배포용 SPRING_ENV_FILE 시크릿과 충돌하지 않는다.

결과

로컬은 그대로 뜨고, 배포를 되살릴 때 DB 주소만 compose가 바꿔 넣으면 된다.

편지 수정·삭제에 소유자 검사 추가

보안

service/LetterService.java · controller/LetterController.java

왜

목록·상세 조회는 이미 findByLetterIdAndUser_UserId로 사용자 기준이었는데, PUT /api/letter/{id}와 DELETE /api/letter/{id}는 findById로 id만 보고 찾았다. 즉 로그인만 되어 있으면 남의 편지 번호를 넣어 남의 편지를 고치거나 지울 수 있었다. 일기에서 이미 고쳤던 것과 똑같은 종류의 구멍(IDOR)이 편지에 남아 있던 것이다.

어떻게

일기와 같은 방식으로 "내 편지 중에서 찾는" 통로 하나를 만들고 수정·삭제가 모두 그곳을 지나게 했다. 먼저 찾고 나서 소유자를 비교하는 방식은 비교를 빠뜨리기 쉬워서, 아예 쿼리 단계에서 걸러낸다.

남의 편지 번호를 넣으면 없는 편지와 똑같이 취급되어 "그 번호의 편지가 존재하는지" 여부조차 새어 나가지 않는다.

결과

실제로 검증했다. 사용자 A가 만든 편지를 사용자 B의 토큰으로 수정·삭제 요청하면 둘 다 거절되고, 편지 내용은 A가 고쳐둔 값 그대로 남아 있었다.

함께 고친 것 — 엔티티를 그대로 응답에 실던 문제

편지 저장 API가 Letter 엔티티를 그대로 반환하고 있었다. Letter는 User를 참조하므로 직렬화될 때 사용자 정보가 통째로 따라 나간다 — password 해시까지 포함해서. 조회 API들이 쓰던 LetterResponse로 통일했다.

함께 고친 것 — 수정하면 작성 시각이 날아가던 문제

Letter.update()가 요청 값으로 createAt을 덮어쓰고 있었다. 클라이언트가 그 값을 빼먹으면 NOT NULL 컬럼이 null이 되어 저장이 깨진다. 일기에서 겪었던 것과 같은 문제다. 작성 시각은 수정 대상이 아니므로 메서드 인자에서 아예 빼고, 쓰이지 않던 UpdateLetterRequest.createAt도 지웠다.

도착한 편지는 고칠 수 없게

기능

service/LetterService.java · exception/BusinessRuleException.java · utils/letter.js

왜

편지 수정 화면을 붙이면서 생긴 질문이다. 이미 받아 본 편지도 고칠 수 있어야 하나? 고칠 수 있게 두면 과거의 내가 쓴 글을 지금의 내가 다시 쓰는 셈이라 타임캡슐이라는 전제가 무너진다. 그래서 막기로 했다.

화면에서 버튼만 숨기는 건 의미가 없다. API를 직접 호출하면 그만이므로 서버에서 막고, 화면은 누를 수 없는 버튼을 보여주지 않는 역할만 한다.

결과

비밀번호가 틀리면 로그아웃되던 문제

보안

service/UserService.java · exception/BusinessRuleException.java

왜

비밀번호 변경 화면을 만들고 일부러 현재 비밀번호를 틀리게 넣어봤더니 로그인이 풀려 버렸다.

원인은 401을 두 가지 뜻으로 쓰고 있었다는 데 있었다. 로그인 실패 문구를 정리하면서 만든 InvalidCredentialsException이 비밀번호 변경 실패에도 쓰이고 있었는데, 이게 401로 나간다. 프런트의 http.js는 401을 "토큰이 만료됐다"는 신호로 읽도록 되어 있어서, 토큰 재발급을 시도하고 그마저 실패하자 세션을 정리해 버린 것이다.

어떻게

상태 코드를 400으로 바꿨다. 401은 "당신이 누구인지 확인할 수 없다"는 뜻인데, 이 요청은 이미 인증을 통과했다. 토큰은 멀쩡하고, 틀린 건 본문에 담아 보낸 값이다. 그건 인증 실패가 아니라 입력값 검증 실패다.

로그인 실패는 401 그대로 두었다. 그쪽은 정말로 인증이 안 된 상태이고, 애초에 토큰 없이 보내는 요청(auth:false)이라 재발급 로직을 타지도 않는다.

결과

다시 재현해보니 400이 돌아오고, 화면에 "현재 비밀번호가 올바르지 않습니다."가 뜨며 마이페이지에 그대로 머문다.

배운 것

상태 코드는 클라이언트가 분기하는 스위치다. 같은 코드에 두 가지 뜻을 담으면 클라이언트가 반드시 하나를 오해한다. "인증 자체가 안 됐다"(401)와 "인증은 됐는데 값이 틀렸다"(400)는 반드시 나눠야 한다.

비밀번호 변경·회원 탈퇴·편지 수정은 백엔드에만 있고 부르는 곳이 없었다. 호출되지 않는 API는 동작을 검증할 방법도 없어서, 실제로 이번에 화면을 붙이자마자 양쪽 모두에서 버그가 나왔다. (위의 두 항목이 그것이다)

어떻게

마이페이지를 세 덩어리로 다시 짰다.

  • 프로필 카드 — 기존 정보와 통계
  • 계정 설정 카드 — 닉네임 · 비밀번호를 같은 모양의 구획으로
  • 위험 구역 — 회원 탈퇴만 따로, 붉은 톤으로 분리

편지 쪽은 보낸 편지함의 카드에 「고쳐 쓰기」·「삭제」를 달았다. 카드 전체가 <button>이던 구조라 버튼 안에 버튼이 들어가는 잘못된 마크업이 되므로, 바깥을 <div>로 바꾸고 "본문을 누르는 영역"만 버튼으로 남겼다.

되돌릴 수 없는 동작은 ConfirmDialog 하나로 통일했다. 편지 삭제는 확인만, 회원 탈퇴는 아이디를 직접 입력해야 버튼이 열린다.

결과

백엔드에만 있던 기능 세 개가 실제로 쓰이게 됐고, 그 과정에서 로그아웃 버그와 탈퇴 실패 버그를 찾아 고쳤다.

탈퇴하면 실패하던 문제 — 남은 데이터와 토큰 사본

보안

service/UserService.java · controller/UserApiController.java · service/TokenService.java

왜

탈퇴 화면을 붙이고 눌러보니 두 가지가 드러났다.

  1. 일기나 편지가 하나라도 있으면 탈퇴가 실패한다. diary.user_id·letter.user_id는 NOT NULL 외래 키인데 JPA cascade를 걸어두지 않아서, 부모인 user를 먼저 지우려 하면 제약 위반으로 막힌다. 데이터가 없는 새 계정으로만 테스트했다면 못 봤을 문제다.
  2. 계정을 지워도 Redis의 refreshToken 사본이 남는다. 그러면 탈퇴한 아이디로도 최대 24시간 동안 accessToken을 계속 재발급받을 수 있다.
어떻게

삭제 순서를 자식 → 부모로 명시하고, 컨트롤러에서 Redis 사본과 쿠키까지 함께 정리하게 했다. 로그아웃과 탈퇴가 같은 쿠키 삭제 로직을 쓰도록 헬퍼로 뽑았다.

결과

일기 1건·편지 1건을 가진 계정으로 탈퇴해 200을 확인했고, 같은 아이디로 다시 가입해 조회하니 일기 0건·편지 0건이었다. 이전 데이터가 새 계정에 딸려오지 않는다는 뜻이다.

잘못된 요청 본문이 500으로 보고되던 문제

운영

config/GlobalExceptionHandler.java

왜

이번 검증 중에 우연히 발견했다. 터미널에서 한글이 깨진 채로 요청을 보냈더니 500 "서버에 문제가 발생했습니다"가 돌아왔다. 실제 원인은 Invalid UTF-8 start byte — 서버가 아니라 요청이 잘못된 것이었다.

500으로 보이면 원인을 서버에서 찾게 되어 디버깅이 크게 돌아간다. 실제로 이 때문에 잠깐 코드를 의심했다.

어떻게

HttpMessageNotReadableException(JSON 형식 오류, 인코딩 오류, 날짜 형식 불일치 등)을 400으로 처리하는 핸들러를 추가했다. 사용자에게는 기존 문구를 그대로 주고, 콘솔에는 근본 원인을 남긴다.

결과

요청이 잘못된 경우와 서버가 잘못된 경우가 상태 코드로 구분된다.

실행 방법

Docker 없이 로컬에서 띄우는 순서

  1. MySQL 확인

    윈도우에 설치된 MySQL이 3306에서 실행 중이어야 한다. .env의 DATABASE_DB 이름으로 된 데이터베이스가 있어야 하며, 테이블은 ddl-auto: update가 첫 실행에 만든다.

  2. Redis 실행

    WSL 안에 설치돼 있다. PowerShell에서 wsl로 진입한 뒤 sudo 없이 실행한다.

    redis-cli ping이 PONG을 내면 성공. exit으로 나가도 계속 살아 있다.

  3. 백엔드 기동

    IntelliJ 실행 구성에서 EmoLetter BE (local)를 고른다. Dockerfile 구성을 고르면 “Server Docker not found”가 뜬다. 터미널을 선호하면 EmoLetter_BE/run-local.ps1이 .env를 읽어 그대로 띄운다.

  4. 프론트엔드 기동

환경변수는 자동으로 읽히지 않는다

build.gradle에 dotenv 의존성이 없어 스프링은 .env를 스스로 읽지 못한다. 그동안은 Docker의 env_file이 대신 넣어주고 있었다. IntelliJ 실행 구성은 envFilePaths로 .env를 직접 읽도록 설정해두었고, run-local.ps1은 CRLF까지 처리해 환경변수로 주입한다.
